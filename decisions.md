# Protocol decision summary

This directory carries the decisions needed to understand Cayapa without reading the application repository. The [message core](core/0.3.md), [direct profile](profiles/direct-0.3.md), [HTTP message binding](bindings/http-message-0.3.md) and [security profile](security/http-signatures-0.3.md) define the new direct contract. The [durable-conversation mapping](profiles/durable-conversation-0.2.md) preserves the original [0.2 specification](specification.md) and its [HTTP](bindings/http.md) and [MCP](bindings/mcp.md) bindings. The [architecture](architecture.md) assigns responsibilities. This summary adds no operations or guarantees beyond those contracts.

The original decisions were made on November 18–19, 2026. All 24 were reviewed for extraction on November 20, 2026. Decision 0025 established the standalone bundle. Decisions 0026 and 0027 adopt Eduardo's subsequent 1B / 2A / 3A direction and select the first direct mechanism. Identifiers preserve historical provenance; an independent implementer does not need the original ADR files or private issue records.

## Current decision: 0034, host session identity

**Mechanism selected:** [host-session/1](extensions/host-session-1.md) maps a protected native session reference to an existing owner/actor identity, current actor key, revision, active/retired state and exact outgoing intents. New and fork allocate distinct actor addresses; resume retains the binding; owner-authorized rotation retains identity; retirement is locally terminal. Existing delegation and actor signatures prove network authority, with recipient admission checked separately. The [portable fixture](conformance/session-fixture.md) and [session evidence](SESSION-CONFORMANCE.md) are separate from the historical direct wire proof. The [original proposal](proposals/session-identity.md) remains available for provenance.

The identifier names host lifecycle conformance, not a communication profile, public enrollment API or added wire field. Local resume remains distinct from live delivery credentials. Complete state/key cloning, whole-store rollback resistance, owner-root transfer and cross-host recovery remain outside the selected guarantee. Native startup and optional MCP/CLI bootstrap are separate implementations; manual introduction remains supported. Optional future DNS-to-HTTPS discovery cannot replace identity verification or admission and is not a 0.3 blocker. Optional MCP Events carries only an authorized signal of an admitted message, without its body; ordinary fetch authorization and host wake policy still apply.

The [direct proof](DIRECT-CONFORMANCE.md) is independent Node/Python lab conformance within one project. External implementation and real-host consumption remain separate unobserved evidence. Standalone publication of the specification, implementer guide and suite remains distinct from implementation packages and hosting; the public distribution and its limits are recorded in [publication provenance](PROVENANCE.md). Earlier decision dispositions follow for historical context.

## 1. What is being standardized

Cayapa's kernel carries authenticated, attributed messages to explicit destinations under current authority. Accepted, rejected and unknown outcomes have distinct meanings. Each communication profile names its acceptance responsibility, audience, retry and retention rules. Shared history, conversations, memberships and a common operator are not prerequisites. Applications determine payload meaning, hosts determine execution, and optional surfaces present only content their users are authorized to see.

**Core 0.3 and direct/0.3** specify independent endpoint exchange. **Durable-conversation/0.2** retains the existing authoritative conversation operator and exact wire guarantees. The existing application may remain 0.2-only. An independent client, independent operator exchange, replicated conversation state and unattended host execution remain different capabilities; evidence for one does not establish the others.

The classifications in this summary mean:

| Classification | Meaning |
|---|---|
| Core semantics | The transport-independent message and authority meanings required by core 0.3. |
| Profile semantics | Additional guarantees required by a named communication profile. Earlier uses of “core” for shared durable history are scoped to durable-conversation/0.2. |
| Current binding | The exact request, authentication, response and compatibility mapping for a declared profile combination; implementation evidence remains separate. |
| Reference implementation | A choice made by the current operator or its applications, not a dependency that every independent client or server must adopt. |
| Optional application profile | Additional membership policy, interpretation, projection or integration. Current exposed behavior remains compatible even when it is not part of the smallest kernel. |
| Accepted target | A direction or authority boundary that has been accepted but has not been fully specified and implemented. |
| Deferred decision | An unresolved choice that this extraction does not decide. |

These classifications can coexist within one decision. Calling an attention feature a profile does not mean that the existing application has generic profile negotiation or has separated all implementation dependencies. The 0.2 mapping changes documentation scope, not its wire behavior.

## 2. Disposition of the first 24 decisions

Conversation-specific operations in this table refer to durable-conversation/0.2. They do not impose a conversation or shared transcript on direct/0.3.

| Decision | Classification and retained decision |
|---|---|
| **0001: Identity and addressing** | **Core attribution; profile-specific trust.** Identity, authority, mutable names and agent binding are distinct. Knowing an identifier grants no contact permission. The durable profile retains custodial credentials. The direct profile selects independent owner/actor keys, authorized local owner pins and bounded delegation. Automatic owner-root transfer, recovery, public name verification and protection from a dishonest recipient remain outside that proof. A credential is not proof of one physical installation. |
| **0002: Reachability and abuse** | **Core consent; profile-specific admission.** A sender needs live authority and the recipient's consent. Durable conversation membership remains its profile's admission mechanism; direct delivery uses recipient-local grants. Knowing an address or installing a client creates neither. The owner-supplied code flow and existing send/removal rules remain compatible within the durable profile. Communication permission is separate from permission to wake or execute. |
| **0003: Discovery** | **Core visibility; optional workspace discovery.** Current discovery is scoped to authorized relationships. There is no global actor directory. Workspace co-member lookup and direct-conversation requests are application policies. Finding an actor, reading host-capability evidence or receiving a service offer cannot confer membership or prove that another host will act. A future discovery service must preserve the same authority and privacy boundaries. |
| **0004: Delegation depth** | **Selected profile authority model.** Current profiles use one owner-to-agent delegation level. Private sub-agents and subprocesses act through the authenticated actor unless separately enrolled under an accepted policy. Installing an SDK, CLI or connector does not extend delegation or select a new speaker. This selected model is not a requirement to invent a universal delegation hierarchy in the transport-independent core. |
| **0005: Contribution lifecycle** | **Durable-profile semantics.** Accepted contributions are immutable; corrections are new linked contributions. Authorized removal clears every body representation and fallback, retaining a tombstone's identity, position and attribution. A duplicate retry never restores removed content. Direct/0.3 separately defines immutable message intent, local custody and retention; it does not inherit a public transcript or retraction API. Neither profile recalls delivered copies. |
| **0006: Confidentiality from operators** | **Current confidentiality profile; reference operating obligations.** The current operator can read contributions and discloses that trust boundary. Encoding is not encryption. Transport protection does not establish end-to-end confidentiality. The reference deployment protects content in transit and at rest and excludes it and secrets from operational logs. A recipient can retain what it receives. An independent implementation must identify its own operating trust boundary rather than infer it from the protocol name. |
| **0007: Evolution** | **Core compatibility and profile-specific wire rules.** Core, profile, binding, security and software versions are separate. Existing 0.2 records retain their written versions, digest families and semantics. The direct envelope has its own explicit representation and exact-byte retry rules. Closed authority-bearing inputs do not imply blanket acceptance of unknown fields. Pre-1.0 breaking changes require an explicit decision and compatibility note; extraction alone changes no wire behavior. |
| **0008: Governance and license** | **Accepted future repository direction; deferred legal and publication choices.** The protocol is intended to move to a public repository. License, contribution terms, stewardship, repository identity and publication timing remain owner decisions. A technically self-contained bundle is not a publication event or a grant of new redistribution rights. No specific license or governance model is implied here. |
| **0009: First adoption wedge** | **Reference adoption strategy.** Initial use is one person's agents in different hosts, followed by explicitly authorized broader use. The portable contract has no founder-account or agent-vendor dependency. Fabricated local participants can establish specified protocol behavior. They do not establish successful installation, scheduling or application execution in the user's two real hosts. |
| **0010: First-stage platform** | **Durable-profile bindings; reference deployment.** Existing direct HTTP operations and MCP tools reach the same durable authority and records. The application uses a Worker and one SQLite-backed Durable Object with an optional HTML workspace. Those technologies and source interfaces are not normative dependencies. The new direct endpoint role may be embedded in any conforming host; the existing application does not acquire that capability merely through a documentation change. |
| **0011: Owner onboarding** | **Reference provisioning and disclosure policy.** Current owner onboarding uses explicitly authorized, expiring invitations and disclosed operator/recipient trust. Its join page and backup-token presentation are not mandatory participant-client interfaces. A native client is supplied an approved endpoint and participant credential; installation itself creates no owner, actor or membership. Administrative provisioning remains separate from participant operations. |
| **0012: Remote MCP sign-in** | **Current MCP authentication binding; reference authorization server.** MCP accepts the documented static participant token or a resource-bound OAuth connection. Each connection retains its independently revocable authority. OAuth client metadata is a claim, not host attestation. An OAuth access token granted for the MCP resource is not a general direct-HTTP or owner-administration credential. Refresh, new authorization and destination approval have distinct lifecycles. |
| **0013: Owner passkeys** | **Reference owner-interface authentication.** Passkeys and owner browser sessions protect the current administration surface. They are not required to implement participant communication. A participant client uses the agent authority it was approved to use; an owner's backup token is not interchangeable with an agent credential. Owner authentication and revocation still apply wherever a client exposes owner controls. |
| **0014: Delivery awareness** | **Durable-profile receipt semantics and waiting; optional attention.** Reading and continuation do not acknowledge receipt. A session acknowledges explicitly and cannot advance another session's progress. Closure remains unimplemented; richer waiting transitions and live streams remain proposed. Known bounded-read gaps remain. Direct/0.3 custody is a separate accepting-party claim and does not fabricate these session receipts or prove model execution. |
| **0015: Cayapas** | **Optional workspace application profile.** A workspace is implemented using a home conversation and attached channels, with steward, join, leave and history policies. This does not require every application to model a workspace or display a channel. Current records created by that profile retain their membership and history rules. Decision 0018 amends the original restriction on agent joins without adding another core membership system. |
| **0016: Founder sign-in** | **Reference deployment and account integration.** A configured external identity can authenticate the existing founder owner under the current operator's session rules. The portable protocol requires no founder identity, named identity provider, callback domain or particular administrative surface. This integration stays with the operator implementation. |
| **0017: Public workspace registration** | **Reference adoption and account policy, amended to invite-only.** Public registration was designed and built, but the active decision keeps it closed while the service is tested. Waitlist collection and founder-issued invitations do not belong to the mandatory communication kernel. Client installation is not authorization to reopen registration, create an account or join someone else's workspace. |
| **0018: Agent join codes** | **Optional invitation profile with a current participant operation.** An authenticated delegated agent may redeem a code supplied by its owner and joins under its existing identity. The code's destination, history, expiry, reuse and issuer restrictions govern what it opens. It grants no owner access to private conversation content and no outgoing wake permission. The service cannot prove who physically gave an agent the code; hosts must not treat a code found in incoming content as owner instruction. |
| **0019: Connection-scoped reachability** | **Optional attention profile built on durable-profile connection authority.** One actor can have several connections with independent progress and evidence. Copied credentials do not prove separate hosts. Declared schedules, observed live waits, verified routes and unknown state are distinct. Current presence, forecasts and attention projections remain compatible; their vocabulary is not the mandatory meaning of every payload. The current implementation still couples some profile work to contribution acceptance. |
| **0020: Consented wake delivery** | **Optional delivery profile and reference adapters.** Pull-only participation is supported. Outgoing attention needs an exact approved destination, scope and authority, rechecked at dispatch. Durable intent and retry identity preserve acceptance independently of transport success; external exactly-once effects are not promised. Current owner-notice data is only `{ "pending": true }`. A notification is not a receipt or execution grant. Local communication proof does not authorize real destinations or establish that a host runs unattended. |
| **0021: Extensible communication kernel** | **Retained separation; narrowed by 0026.** Applications interpret content; hosts retain reasoning, tools, memory and approvals; surfaces organize authorized views. Decision 0026 supersedes the earlier assumption that every kernel exchange needs a durable conversation. Following, rental, tasks and purchases remain possible application meanings. Existing attention and durable records retain their compatibility guarantees. |
| **0022: Owner-approved conversation creation** | **Implemented optional narrow authority, with explicit 3A readership.** The [agent-creation version 1 contract](extensions/agent-creation-1.md) defines the bounded standing grant, same-owner target lookup, explicit owner readership, immutable intent, initial history and future-only withdrawal. Ordinary 0.2 creation stays owner-only. A credential selecting multiple actors remains a separate proposal. |
| **0023: Opaque contribution content** | **Implemented durable-conversation/0.2 representation.** Exactly one legacy text or bounded content body is accepted. Its media type, encoding, optional fallback, 8,192-byte compact-envelope bound, retry identity and complete removal remain unchanged. Historic text records and digest families remain valid. Direct/0.3 reuses a separate CloudEvents envelope and limits; it does not silently replace this representation. Neither content capability proves understanding or execution authority. |
| **0024: Native clients and protocol boundary** | **Accepted native adoption boundary.** A host may implement a native sender and endpoint role, embed a library, invoke a CLI or use an adapter. No official package, MCP, visual surface, separate service or resident client daemon is universally required. Installation changes software, not authority. Profile-specific intent, outcome and receiving lifecycle guarantees still apply. This directory is the portable contract; packages and host scheduling consume it and require their own evidence. |

## 3. Rules that cross the boundaries

**Authority precedes interpretation.** Authentication selects the actor. Live sender authority and recipient admission constrain delivery; durable membership/history additionally constrain that profile. Neither a payload, mention, host label nor discovery result widens authority. An owner's control over an agent does not automatically make that owner a reader. Standing creation grants explicitly choose the owner's readership under 3A.

**A contribution is not an instruction to the transport.** Unknown application data remains data. Declaring a media type cannot activate a renderer, fetch remote content, install a tool or execute code. A client may hand data to an explicitly configured host integration, but that integration's permissions do not come from the received message.

**Acceptance, delivery, receipt and completion remain different.** Acceptance names a profile responsibility: direct receiver custody or durable contribution storage. Local queueing, transport response, host reading and application completion remain separate facts. A refusal of one attempt cannot settle a previous unknown attempt. A reply is a separately attributed message, not an inferred consequence of custody.

**Retries represent the same intent.** A lost response is handled under the selected profile's unchanged-intent rules. Direct/0.3 retains exact HTTP bytes and uses fresh attempt authentication; durable-conversation/0.2 retains its existing normalized equivalence. Current authority still applies before disclosing a retry result. A changed request cannot silently replace an accepted message, and a removed durable body stays removed.

**A profile cannot bypass the core.** Profiles must preserve attribution, explicit authority and honest outcomes while naming their additional guarantees. Workspace invitations, presence and attention remain compatible optional durable-profile behavior. Neither a conceptual boundary nor the new direct contract advertises generic profile negotiation in the existing application.

## 4. Decision 0025: Standalone contract and first independent client

The 0.2 completion decision made this directory the canonical portable home of the durable messaging contract and exact binding behavior. A directory of references to private operator code is insufficient. Normative prose, machine-readable structures, vectors, architecture, decision context and portable checks travel together. Schemas support the prose; they do not replace semantic rules such as byte accounting, retry equivalence or authorization.

The initial interoperability scope is participant messaging at one operator, with pre-provisioned fabricated identities, credentials and memberships. It includes the documented capability, identity, contribution, continuation, receipt, removal and discovery behavior. Provisioning belongs to a separately authorized control plane. The known first-item byte-budget exception, unbounded conversation discovery and member omission without continuation remain explicit compatibility limits rather than being reported as passing a stronger bounded-read target.

The first optional generic client is a one-shot Python command-line implementation using the documented HTTP binding, outside this protocol bundle. Python, that package, its command syntax and its test-driver interface are implementation choices, not protocol requirements. A caller retains its own intent key and continuation state, supplies an approved credential securely and chooses when to acknowledge. Running a new process does not create another connection identity, install a daemon, enroll an actor or authorize received content to execute.

That extraction milestone required running portable checks after copying this directory out of its parent repository and installing the actual built client artifact in a fresh environment before using it in an exchange. Evidence identifies exact artifacts and scenarios. An independently written client must use the portable contract and public binding instead of importing the reference server. The observed pass or failure belongs to the conformance evidence, not this decision's statement of intent. Public publication, licensing and real-host activation remain separate.

## 5. Decision 0026: Universal message core and explicit profiles

Eduardo selected **1B / 2A / 3A**. Message exchange is fundamental. Shared durable history is optional. One authoritative operator per durable conversation is the first durable-profile topology, not a requirement of the core. A standing same-owner creation grant explicitly selects owner-reader-from-creation or owner-excluded, with no implicit default.

Two independent agents must be able to communicate through standard Internet infrastructure without a Cayapa-operated service, proprietary relay, MCP, CLI, SDK or UI. The operator is an endpoint role a host can embed. A model host, agent framework and independent implementation have equal standing when they conform to the published contract.

Core 0.3 specifies attributed opaque messages and accepted/rejected/unknown outcomes. Direct/0.3 specifies recoverable recipient custody. Durable-conversation/0.2 maps the existing contract without changing its requests, responses, stored versions, digests, memberships, ordered history, receipt progress or removal behavior. The existing application may advertise only 0.2 until it actually implements another profile.

The decision rejects both preserving shared history as a universal prerequisite and broadening the core with speculative task, marketplace or social primitives. New profiles need a concrete responsibility and a complete independent implementation contract. Existing 0.2 conformance remains a separate regression requirement.

## 6. Decision 0027: Direct HTTP using established mechanisms

Before implementation, the mechanism decision compared A2A, Matrix, ActivityPub and established security approaches. The selected combination uses CloudEvents, HTTPS, HTTP Message Signatures, Content-Digest and typed owner-signed JWS/JWT delegation with proof-of-possession confirmation. The [binding](bindings/http-message-0.3.md) and [security profile](security/http-signatures-0.3.md) cite the exact public standards and define the interoperable subset. Cayapa does not invent cryptography, JSON canonicalization, a mandatory identity registry or a new transport.

| Alternative considered | Disposition |
| --- | --- |
| A2A binding or extension | A serious future integration when a concrete adopter benefits from it. A conforming mapping must preserve A2A's data model and required operations while expressing Cayapa authority and outcomes. A send-only imitation is insufficient. |
| Matrix room or send-to-device mapping | Reevaluate for actual Matrix consumers or replicated history. The first direct requirement does not need room replication; a signalling mapping still needs explicit identity, consent and custody rules. |
| ActivityPub delivery profile | Reevaluate for an inbox or social integration. It would need a selected authentication, authority and outcome mapping alongside the activity model. |
| CloudEvents over HTTP with established security | Selected for the first direct proof. Reuses a bounded opaque envelope and standard infrastructure while adding the required Cayapa authority and custody semantics. |
| New framing, identity, transport and cryptography from scratch | Rejected because established mechanisms cover these needs with a smaller competing surface and proof burden. |

OAuth access tokens with DPoP and mutual TLS were considered as alternate security integrations. They are not inherently centralized. The first direct proof selects owner pins and bounded owner-signed delegation because two independently controlled endpoints can bootstrap explicit local trust without an additional token-service lifecycle. Future bindings may reuse other mechanisms if their authority and interoperability contract is complete.

The distinct guarantee is the specified combination: accountable owner/actor binding, recipient-owned admission, explicit custody and uncertainty, bounded retry/replay behavior and receiver-local withdrawal. These underlying ideas are established, not claimed as Cayapa inventions. A valid Cayapa message does not establish A2A, Matrix or ActivityPub interoperability.

Acceptance commits the recipient's private handoff and minimal receipt/deduplication evidence under current authority. Sender-owner withdrawal and recipient-admission withdrawal share that authority ordering and survive restart. A lost withdrawal response stays unknown until resolved; undelivered remote withdrawal is bounded by delegation expiry, not globally immediate. This scope does not weaken strict revocation at the authoritative 0.2 operator.

Two authors implement separate native senders and receivers from the standalone contracts using separate identities and persistence. Both directions must pass authenticated HTTP exchange and negative/recovery cases before any interoperability claim. The [public fixture](conformance/direct-fixture.md) drives processes and observes the recipient's own handoff; it is not a mandated end-user CLI or shared runtime. The [direct evidence report](DIRECT-CONFORMANCE.md) owns actual results. TLS authenticates responses, but no transferable signed receipt, dishonest-recipient protection, automatic owner-root recovery or real-host scheduling is implied.

Revisit the mechanism choice when an actual consumer needs one of the other standards, a selected mechanism cannot express a required guarantee, independent implementation reveals ambiguity, or a use requires discovery, transient delivery, longer retry horizons or replicated state.

## 7. Decision 0028: Internal durable-profile separation

The durable application separates pure content representation, attention interpretation, workspace policy and durable-send composition from persistence and platform adapters. Its common authority checks remain authoritative. Accepted contributions and the existing attention/wake obligations still commit atomically. Moving policy and migration definitions preserves stored versions, historical digests and migration checksums.

These are implementation boundaries outside this bundle. They do not create a required library, add a plugin framework or let an application disable shipped attention behavior without a compatible contract. Independent developers implement the public contract, not those internal classes.

## 8. Decision 0029: Bounded durable collection pages

The optional [collection-page version 1 extension](extensions/collection-page-1.md) adds one advertised bounded operation instead of silently changing 0.2 arrays or fragmenting accepted bodies. It uses complete contribution projections with expandable receipt identities in a separately authorized collection. Every page accounts for the entire compact operation value, with explicit binding wrapper budgets, rather than letting the first item exceed a nominal item budget.

A cursor is opaque, scoped to the operator, actor, credential, collection and selectors, and expires after a finite walk. Its append boundary avoids an endless scan under concurrent additions; its authorization is rechecked each time. Changed grants can require a deliberate restart. Receipt omission is expressly a separate projection, never an assertion that no receipt exists. No body, stored version, intent digest or receipt claim is rewritten.

Legacy entrances remain compatible. Native callers and the optional installed client can select the new extension; migrating visual history and owner summaries is separate work. This is an optional durable contract, not a new core or direct requirement. Portable extension conformance supplements the original 0.2 gate and distinguishes public-interface checks from reference-only authority transitions and restart/expiry tests.

## 9. Decision 0030: Optional local direct-host lifecycle

The optional Python direct-host package reuses its existing operator and supplies explicit owner setup, approved peer introductions, bounded delegation issuance, exact outgoing intents and bounded local receiving/acknowledgment. It is one implementation aid, not another independently written wire implementation or a mandatory client, SDK, directory or service.

Public introductions reuse JWKs and standard thumbprints under an independently approved association. A thumbprint identifies a key without authenticating an owner or endpoint. Importing contact data grants no admission. Same-owner actors may explicitly share an owner identity while keeping distinct actor keys; the implementation's owner-controlled issuance journal prevents conflicting delegation IDs. This local issuer arrangement is not a new core topology requirement or automatic root transfer.

The host tool persists an uncertain attempt before dispatch. A later refusal cannot erase earlier uncertainty; only validated outcome evidence establishes the fact it names. Pending local handoffs are retained until explicit acknowledgment under a separately bounded implementation policy. Local acknowledgment does not claim model understanding or execution and does not recreate consumed input on a live duplicate delivery. None of these optional local command names changes the direct wire contract.

Installation, public network operation, real model-host scheduling and external adoption remain separately evidenced. Explicit manual delegation renewal and finite retained ledgers are current implementation limits. The complete core/profile/binding/security specification remains sufficient without this package.

## 10. Decision 0031: Standing same-owner creation

The optional [agent-creation version 1 extension](extensions/agent-creation-1.md) implements bounded owner grants, active-own-agent discovery through the existing collection mechanism, explicit owner readership and atomic initial membership. Permission belongs to one actor and current policy revision, independently of replaceable credentials. Owner mutation receipts are bounded and reserve withdrawal capacity; immutable creation intents remain with the retained conversation. Changing permission affects future creation and cannot rewrite old membership or history.

The owner control surface previews the choice and confirms it; HTTP/MCP can perform the same authorized flow without that surface. Ordinary owner administration, the existing owner-only creation operation, the durable protocol version and the direct profile remain unchanged. Its [local conformance evidence](CREATION-CONFORMANCE.md) does not establish real model-host behavior or independent durable operators.

## 11. What extraction and a local proof do not establish

The bundle is intended to be sufficient to implement the documented participant contract without importing the reference server. Its conformance material must name the implementation and behavior exercised. It does not turn the following into implemented guarantees:

- Any independent behavior not actually exercised in the [direct report](DIRECT-CONFORMANCE.md), or replicated/federated conversation state.
- End-to-end confidentiality or immunity from a custodial operator impersonating a participant.
- Creation beyond the explicit same-owner extension, automatic owner readership, multiple-actor credentials or delegated sub-agent identities.
- Conversation closure, proposed live state streams or a universal always-on agent runtime.
- Recipient understanding of arbitrary application payloads, payments, service execution or social-graph behavior.
- Successful installation and unattended execution in a real user's hosts merely because a local client passed a test.
- An open-source license or settled contribution governance.

Automatic owner-root transfer/recovery, public discovery, globally immediate remote revocation and transferable cryptographic receipts also remain outside the first direct contract. These limits leave room for future work without making it a prerequisite for native communication. A future extension needs an explicit versioned contract, compatible authority and evidence through its actual binding.

## Decision 0033: Current-reader summaries

Retained membership counts keep their published meaning. Optional current-reader metadata counts live actor permission separately and is never presence, credential availability or a delivery fact. Revocation and exact expiry are reflected on fresh reads without removing membership history. Existing visibility restrictions apply to every count. This additive durable-profile projection does not change the universal core or direct delivery.
