# Cayapa message core 0.3

Status: normative contract; implementation and interoperability evidence are reported separately. Requirements use MUST, MUST NOT, SHOULD and MAY in the sense of RFC 2119 and RFC 8174.

## 1. Scope

Cayapa enables independently implemented actors to exchange opaque messages under accountable, revocable authority. Its core is transport independent. A conversation, shared history, common database, task, global sequence, visual surface, official SDK, CLI, MCP adapter, proprietary relay or Cayapa-operated service MUST NOT be a prerequisite of core communication. A host may implement an endpoint itself or authorize a separately operated service.

A **message** is one attributed intent to communicate opaque content to a declared destination. A **delivery** is an attempt to transfer that message under a selected communication profile. An **operator** runs an implementation of communication responsibilities; that role may be embedded in an agent's host. An **owner** is the person or organization accountable for an **actor**. Identity, authorization, recipient admission and readership are distinct.

The core defines semantics, not a JSON object or cryptographic algorithm. A binding maps them to a wire representation. A communication profile supplies additional guarantees such as durable shared history. Application profiles interpret payloads and cannot manufacture authority.

## 2. Common message information

Every supported exchange MUST unambiguously establish:

| Information | Requirement |
|---|---|
| Core and required profile | The sender and receiver agree which guarantees apply. Unsupported required behavior is refused before acceptance. |
| Message identity | A stable identity within the authenticated actor's namespace. Attempts to deliver the same intent retain it. A profile defines its destination scope, retry equivalence and retention horizon. |
| Actor and accountable owner | Attribution is checked through the binding's authentication and authority mechanism, not accepted from payload claims. |
| Destination and audience | The intended logical recipient or authorized audience is explicit. A network route is distinct from an identity. Knowing either grants no admission. |
| Opaque content | Declared representation and exact content are preserved under the selected profile. A receiver need not understand an application's vocabulary. |
| Authority and validity | Sender delegation and recipient admission are live at the profile's acceptance boundary. Limits, expiry and effective revocation are explicit. |
| Outcome | The accepting authority and responsibility assumed are identifiable. Transport progress and application execution remain separate facts. |

Profiles MAY add correlation, a history context, ordering, receipt stages or retention. None is inferred from an application payload or the word Cayapa. A message can contain any application-defined data within the advertised representation and bounds. Payloads MUST NOT be executed, fetched, or treated as authority merely because delivery succeeds.

## 3. Authority

An actor's permission to send on its owner's behalf and a recipient's permission to accept that sender MUST be verified independently. A valid sender identity does not oblige a recipient to accept communication. Standing grants can provide consent in advance within declared limits; no per-message human interaction is required by this core.

An owner's authority over an agent MUST NOT automatically make the owner's person identity a reader of every message or conversation. A communication profile defines its audience. The durable same-owner creation policy separately requires an explicit readership choice in the standing creation grant.

A security profile MUST state trust bootstrap, which party can attest to ownership, how possession of a credential is proved, its validity and scope, and what authority withdrawal means. It MUST distinguish receiver-local withdrawal from knowledge of a remote change. Authentication, consent and retained outcome access are rechecked at the applicable operation boundary.

## 4. Delivery outcomes and recovery

| Outcome | Core meaning |
|---|---|
| Accepted | The named receiving authority has assumed the responsibility defined by the selected profile for this message. Its exact responsibility MUST be stated. |
| Rejected | This attempt did not create a new acceptance. This alone does not settle whether an earlier uncertain attempt was accepted. |
| Unknown | The caller lacks trustworthy evidence to determine the relevant attempt's outcome. It MUST NOT invent either acceptance or rejection. |

Local queueing, destination acceptance, durable-conversation storage, recipient-host receipt and application execution MUST remain distinguishable. A generic successful response from another protocol is insufficient evidence of Cayapa acceptance.

A sender reconciling uncertainty MUST retain the same message identity and profile-defined immutable intent, then use the profile's retry/reconciliation procedure. It MUST NOT silently create a new identity, change expiry or weaken the required profile. Profiles MUST define duplicate, changed-intent, expiry, replay, current-authority and restart behavior, including the duration of any deduplication guarantee. Exactly-once execution of application effects is outside this contract.

## 5. Compatibility and profiles

| Profile | Contract | Version relationship |
|---|---|---|
| `direct/0.3` | [Direct delivery](../profiles/direct-0.3.md), [HTTP mapping](../bindings/http-message-0.3.md), [security](../security/http-signatures-0.3.md) | First native binding of core 0.3; no conversation provisioning. |
| `durable-conversation/0.2` | [Mapping and preserved guarantees](../profiles/durable-conversation-0.2.md); existing [specification](../specification.md) and HTTP/MCP mappings | Existing 0.2 wire values and stored data are preserved. This is an explicit legacy profile mapping, not an automatic wire upgrade. |

Core, profile, binding, security profile and software package versions are separate. Support MUST be advertised only where implemented, and acceptance must establish the profile actually used. A bridge MUST reject a required guarantee it cannot preserve; it cannot claim conformance by carrying bytes while discarding authority, outcomes or history requirements. Future direct, mailbox and replicated-history profiles are permitted but not defined by this release.

## 6. Independent implementation and conformance

An independent developer MUST be able to implement a supported profile from this bundle, its explicitly referenced public standards and the conformance suite without application source, private issue trackers or an official library. Normative requirements take precedence over examples and test coverage.

Conformance claims identify the core/profile/binding/security versions, implementations and authoring inputs, trust bootstrap, identities, storage boundaries, transport, exact cases and failure schedules. Passing one profile does not imply every profile. A loopback experiment does not prove public deployment, production operations, autonomous model execution or malicious-operator resistance. The [evidence index](../CONFORMANCE.md) owns observed claims.
